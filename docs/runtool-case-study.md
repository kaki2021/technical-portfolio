# Runtool：从自动化脚本到统一测试平台

> **项目性质：任职期间内部项目的脱敏复盘**  
> 本文只保留本人负责部分的工程思路、需求演化与抽象后的架构。原公司源码、内部模板、客户信息、真实业务数据、账号、路径、工具配置与其他受限内容均不公开。

## 1. 项目概述

- **时间：** 2024.01–2025.07
- **角色：** 主导开发（个人）
- **场景：** EDA / 软件工具测试团队的批量测试、结果统计与日常信息汇总
- **核心问题：** 测试功能多、需求变化快、重复操作多，单次脚本能快速解决问题，但随着脚本和需求增长，维护、复用、统计与团队协作成本迅速上升。

这个项目不是从一开始就设计成“平台”。它首先是为了解决一个具体需求而写的特异性脚本，之后随着真实使用逐步演化。

---

## 2. 最初：先把单个需求做出来

早期目标很直接：**尽快得到本次需求的结果**。

典型脚本会把工具、参数、设计文件和执行命令直接写在一起。这样做的优点是开发快，能够迅速完成单个任务；但当需求不断增加后，问题开始出现：

- 可用脚本越来越多，成员很难知道“现在有哪些脚本、该用哪个”；
- 多个脚本重复执行相同步骤、调用相同文件；
- 公共文件或流程发生变化时，需要逐个脚本修改；
- 相似代码大量复制，长期维护成本持续上升。

### 阶段结论

**特异性脚本适合快速响应，但不适合无限增长。**

---

## 3. 第二阶段：把重复逻辑合并

当不同需求之间出现明显的重复步骤后，我开始把公共变量、执行逻辑和参数入口统一起来。

这一步解决了两个直接问题：

1. 同一套公共逻辑只维护一次；
2. 团队成员使用统一入口执行任务，为后续标准化统计创造条件。

但新的问题也随之出现：当越来越多需求继续塞进同一个脚本，代码本身会变得难以理解。

- 条件分支越来越多；
- Debug 时难以判断某次修改会影响哪些功能；
- 新旧逻辑之间产生隐性耦合；
- 有些 Bug 可能在修改很久以后才暴露。

### 阶段结论

**“把脚本合在一起”不等于平台化。统一入口之后，还必须继续做结构拆分。**

---

## 4. 第三阶段：从“大脚本”转向模块化

后续设计的重点变成两个问题：

- 如何维持统一入口和统一维护；
- 如何让代码逻辑足够清晰，使新增功能不会持续增加耦合。

我的判断依据之一是：**不同需求到底有多少共性。**

- 共性高的步骤进入公共能力；
- 只有某类需求使用的逻辑留在对应模块；
- 新需求刚出现、交付时间很紧时，可以先用特异性方式快速实现；
- 当需求重复出现、共性逐渐清楚，再把它抽象进入平台。

这使平台不是一次性“设计完”的，而是从实际需求中持续演化。

### 脱敏后的抽象结构

```text
统一入口
   │
   ├─ 参数 / 配置处理
   │
   ├─ 公共流程与通用能力
   │      ├─ 文件与路径处理
   │      ├─ 批量任务
   │      ├─ 结果采集
   │      └─ 日志 / 状态
   │
   ├─ 不同测试需求的差异化模块
   │
   └─ 结果输出与统计
          ├─ 测试报告
          ├─ 结果对比
          ├─ 性能数据
          └─ 日报 / 周报
```

> 上图是为公开作品集重新抽象的表达，并非原公司内部架构图复刻。

## 5. 我如何判断“这个需求要不要写成脚本”

内部分享时，我把这个判断拆成了几个因素：

- 手动完成需要多长时间；
- 脚本开发需要多长时间；
- 当前交付期限有多紧；
- 这个需求未来是否可能重复；
- 脚本是否具有较高通用性。

可以简化为：

```text
如果 手动成本 > 自动化实现成本：
    优先自动化

如果 自动化能在交付前完成 且 复用价值高：
    优先做成通用能力

如果 自动化能在交付前完成 但 复用价值低：
    根据交付压力选择特异脚本或手动处理

如果 自动化开发时间已经超过交付期限：
    先保证交付，再考虑后续抽象
```

这套判断让我避免“为了自动化而自动化”。

## 6. 从需求到结果：把人工工作拆成可执行流程

写脚本之前，我通常先把手动过程拆开：

1. 明确需求；
2. 解构需求里真正需要的数据或结果；
3. 拆分人工操作步骤；
4. 确定脚本需要哪些输入；
5. 通过命令或程序把输入转换成中间数据；
6. 对中间数据继续处理；
7. 以统一格式输出结果。

例如“整理性能数据”这类任务，本质上可以进一步拆成：

```text
需要哪些性能指标
        ↓
每个指标从哪里取得
        ↓
需要哪些输入文件
        ↓
通过什么命令提取
        ↓
如何标准化
        ↓
统一写入 CSV / 报告
```

脚本的价值因此不只是“省几次点击”，而是把工作流程显式化，使输入、步骤和输出逐渐形成统一规格。

## 7. 平台最终承担了什么

项目后期，平台已经不仅是一个“脚本集合”。实际使用中逐步覆盖：

- 统一任务入口；
- 批量测试任务；
- 参数动态配置；
- 测试报告自动生成；
- 结果对比；
- 性能数据统计；
- 日报 / 周报等信息汇总；
- 团队成员使用支持、问题复现和持续优化。

平台由驻场团队 10+ 名同事使用，并替代了相当一部分依赖人工整理的项目进度汇总工作。

我也以《runtool 设计理念与代码说明》为主题做过内部技术分享，把“脚本为什么会逐步变成平台”“如何判断抽象边界”“工具和管理流程是什么关系”等思路整理给团队。

## 8. 已实现能力与“可扩展设想”要区分

原内部分享里还讨论过一些平台继续扩展的方向，例如：

- 更完整的操作记录与数据分析；
- 自动生成工作进度；
- 管理员与用户权限；
- 工作需求统一发布；
- 对平台自身增加回归测试。

这些内容属于当时对统一平台边界的进一步思考，**不应全部等同于已经上线的功能**。公开复盘中，我把“实际完成”和“未来可扩展”明确分开，以避免过度包装项目经历。

## 9. 这个项目让我形成的工程习惯

### 9.1 从真实问题中抽象，而不是先做“大平台”

平台最初只是一个小脚本。只有当重复需求、维护成本和团队协作问题真实出现后，抽象才有明确依据。

### 9.2 统一入口之后，更重要的是内部边界

把几十个脚本改成一个脚本，只是表面统一。真正降低维护成本，需要继续拆公共能力、差异化模块、输入输出和错误定位路径。

### 9.3 自动化同时也是流程分析

只要一个工作能被稳定地自动化，就意味着它的输入、步骤、判断和输出必须被说清楚。这个过程本身会暴露原流程中模糊、重复或不一致的地方。

### 9.4 可观测性和问题复现很重要

面向团队使用后，工具不仅要“能跑”，还要能够通过日志、参数和运行环境快速复现问题，否则维护成本会重新回到人身上。

---

## 10. 与后续自动化和 AI 应用实践的关系

Runtool 不是 AI 项目，但它对我后来做 AI Agent、n8n 和业务系统影响很大。

后续做自动化和 AI 应用时，我仍然沿用相似方法：

```text
真实需求
   ↓
拆输入 / 状态 / 人工步骤
   ↓
先把确定性流程做稳定
   ↓
找到适合模型处理的环节
   ↓
结构化输入输出
   ↓
增加校验 / 日志 / 重试
   ↓
再逐步平台化
```

因此，我更倾向于把 AI 看作流程中的一个能力节点，而不是让模型替代所有确定性逻辑。
